Runtime Layer

How the Orchestrator boots and runs

📚

Skill loading at startup

Reads all SKILL.md files, applies tag filtering (always / vision / content / conversion), and interpolates {{VAR}} from schema.ts. Workflow logic stays in markdown, not buried in code.

🔌

Dynamic MCP tool registration

Calls tools/list at runtime and converts JSON Schemas to typed Zod validators via jsonSchemaToZod. New tools become available without reworking the orchestrator prompt.

🔄

streamText loop + live reasoning

The model runs inside a streaming loop. Text, reasoning, and tool-call chunks emit live thinking SSE events so the UI shows progress rather than a black box.

Control Layer

Why the Orchestrator is the guardrail

🛡️

Tool interception

plan_feedback is intercepted before returning to the model, which pauses the stream and triggers human review. apply_config_update is also mediated before anything reaches the live storefront.

👁️

Two-model vision pipeline

A separate vision-capable LLM extracts precise color and layout tokens first. The primary orchestrator model then plans from structured facts instead of repeatedly re-interpreting raw pixels.

📡

Stateless + resumable

Every HITL resume request carries the full context back into the system. No sticky server session is required, which keeps the backend horizontally scalable and resilient through revision loops.

Tool Protocol

MCP makes the system LLM-agnostic

Why MCP (Model Context Protocol)

Single schema, any caller. Tool definitions live in one place. Any LLM with tool-calling support speaks the same JSON-RPC contract — swap providers without touching the tool layer.
Runtime discovery. The Orchestrator calls tools/list at startup — no hardcoded schemas. Add a tool server-side and the Orchestrator picks it up at the next request with zero code changes.
Swappable orchestrator. Any MCP-compatible client (LangGraph, AutoGen, CI pipeline, another AI agent) can call the same tool server unchanged — the contract is standard.
Validated inputs. JSON Schema → Zod conversion enforces types on every tool call. Malformed LLM arguments are rejected before they reach business logic.

The 5 MCP Tools

analyze_vision_inputExtract dominant style, color scheme, layout type from URL or description
generate_themeMap dominantStyle + aesthetic to full ThemeConfig (colors, font, radius, nav style)
plan_layoutSelect hero layout, section order, grid density, and hero micro-parameters
get_storefront_configRead live config before proposing — the LLM inspects current state before acting
apply_config_updateSubmit design patch — intercepted by Orchestrator into HITL-gated config_update event

Design Principle

The LLM never publishes without explicit human approval

🤖
LLM runs workflow
Calls analyze → generate_theme → plan_layout via MCP. Reasoning streamed live to UI as thinking events.
▼

🚦
Orchestrator intercepts
plan_feedback caught before result returned. Stream pauses. plan_description SSE fires to UI.
▼
approve / reject
👀
Human reviews
Sees planned changes by category. Can approve all, reject items, or add free-text feedback to steer the revision.
▼
approved
🛍️
Config applied
Orchestrator resumes. LLM calls apply_config_update. config_update SSE → Zustand → live preview.
↺ Rejection loop Rejecting sends the previous plan plus human feedback back through the Orchestrator for Phase 2 revision. The loop is explicit, auditable, and repeatable until the human approves.
🔄

Why it matters: The Orchestrator stays stateless while preserving full context on every retry. Every approval, rejection, and revision is written into the audit trail in JSON-RPC form.

End-to-End

One run, step by step

1

User submits goal

Vision URL + optional image → POST /api/orchestrate. SSE stream opens. UI clears previous thinking log.

2

Orchestrator boots

Loads tag-filtered SKILL.md files · calls tools/list on MCP server · runs vision pre-analysis if image present · builds full system prompt.

3

LLM executes Phase 1 — Understand

Calls analyze_vision_input → generate_theme → plan_layout via MCP JSON-RPC. Thinking events stream to UI throughout.

4

HITL gate fires

LLM calls plan_feedback → Orchestrator catches it → emits plan_description SSE → stream stops. UI renders plan approval card.

5

Human approves or revises

Approve → resumeWithFeedback({approved:true}). Reject → feedback + previous plan re-submitted → Orchestrator runs Phase 2 (Revise). Loop repeats until approved.

6

LLM executes Phase 3 — Apply

Calls apply_config_update via MCP. Orchestrator intercepts result → emits config_update SSE → Zustand updates → canvas re-renders live.

7

Human saves (explicit action)

All changes in-memory with 50-step undo/redo. Click Save → PUT /api/store-config → writes store-config.json → web app reflects changes.

Extensibility & Next Steps

Designed to grow without rewrites

🔁

Swap the LLM

One env var (AI_MODEL) changes the model provider. MCP tools and skills are provider-independent. No UI, workflow, or tool code changes needed.

⚙️

Add MCP tools

Add a function to /api/mcp/route.ts. The Orchestrator discovers it at the next request. Ideas: SEO analyzer, A/B variant generator, accessibility checker.

📝

New skills, no code

Add a SKILL.md with a ## Tags section. Loaded and injected automatically. Localization, brand voice, guided copy — all in markdown.
